# Техническое задание: Веб-приложение для учёта компонентов на складе

## 1. Обзор и цель

**Что это:** Веб-приложение для личного/командного учёта электронных (или иных) компонентов на складе.

**Главная цель:** Иметь под рукой актуальный список компонентов на складе.

**Ключевая ценность / что должно стать удобнее:**
Быстро получить ответ на вопрос, что есть на складе, а чего нет. Сразу понимать как выглядит тот или иной компонент.

---

## 2. Пользователи и сценарии

**Кто пользуется:** ✅ несколько пользователей, вход по логину.

**Общий каталог или у каждого свой?**

- [x] У каждого пользователя **свой отдельный** каталог
- [ ] Все пользователи видят и редактируют **один общий** каталог компонентов

**Основное устройство:** ✅ мобильный телефон (mobile-first), десктоп — второстепенно.

**Основные сценарии использования (user stories):**

1. Открываю список компонентов карточками и быстро нахожу нужный.
2. Открываю карточку компонента и вижу подробности + все фото.
3. Добавляю новый компонент с фото и заполняю поля.
4. Редактирую фото / количество / статус / комментарий и т.д. у существующего компонента.
5. Управляю аккаунтом: регистрация, вход, выход.

## 4. Модель данных

> Подход ✅: набор полей компонента **фиксирован и задаётся в коде фронтенда**
> (TypeScript/Zod-схема). Отдельной таблицы с описанием полей нет. Значения всех
> полей компонента, **включая ссылки на изображения**, хранятся одним объектом в
> JSON-поле `data`. Какие поля поддерживаются и где они показываются — решается при
> разработке UI; в базу уходит уже готовый валидный JSON.

### 4.1. `User` — пользователь

| Поле              | Тип                | Описание         |
| ----------------- | ------------------ | ---------------- |
| `id`              | string (cuid/uuid) | идентификатор    |
| `login` / `email` | string             | уникальный логин |
| `passwordHash`    | string             | хеш пароля       |
| `createdAt`       | datetime           |                  |

> Точный набор полей `User` уточняется под выбранное решение аутентификации (NextAuth и т.п.).

### 4.2. `Component` — компонент склада

| Поле        | Тип                | Описание                                           |
| ----------- | ------------------ | -------------------------------------------------- |
| `id`        | string (cuid/uuid) | идентификатор                                      |
| `ownerId`   | string             | владелец (связь → `User`); каталоги у каждого свои |
| `data`      | JSON               | объект со всеми значениями полей компонента (4.3)  |
| `createdAt` | datetime           |                                                    |
| `updatedAt` | datetime           |                                                    |

### 4.3. Набор полей внутри `data` (определяется в коде, не в БД)

Структура `data` описывается схемой в коде фронтенда (напр. Zod) и валидируется
перед сохранением. Предполагаемый набор (уточняется при разработке UI):

| Ключ       | Тип           | Обяз. | Описание                                         |
| ---------- | ------------- | ----- | ------------------------------------------------ |
| `name`     | string        | да    | название компонента (заголовок карточки)         |
| `images`   | string[]      | нет   | ссылки на изображения в S3; первая — главная     |
| `quantity` | number        | нет   | количество                                       |
| `status`   | string (enum) | нет   | статус (напр. в наличии / в пути / отсутствует ) |
| `note`     | string        | нет   | заметка                                          |
| `url`      | string (url)  | нет   | ссылка на магазин                                |

> Изменение набора полей = правка схемы и UI в коде (не через интерфейс приложения).

## 5. Функциональные требования

### 5.1. Список компонентов (главная)

- Сетка карточек в **2 колонки** (стиль маркетплейса: Temu/AliExpress), mobile-first. На desktop можно больше колонок.
- Карточка показывает: главное фото, название и ещё несколько полей (набор определён в коде).
- Переход с карточки на страницу компонента.
- Поиск по названию (обязательно) и другим полям (можно исключить из MVP).
- Фильтры: по полям (можно исключить из MVP).
- Пагинация / бесконечная прокрутка: 50 карточек на странице (mobile).

### 5.2. Страница компонента

- Галерея изображений (несколько фото, главное — первое в `data.images`).
- Все поддерживаемые поля компонента.
- Кнопки «Редактировать», «Удалить».

### 5.3. Создание и редактирование компонента

- Форма с фиксированным набором полей (из схемы в коде), с учётом типа каждого поля.
- Загрузка / удаление / переупорядочивание изображений.
- Назначение главного изображения (первое в `data.images`).
- Валидация обязательных полей и типов (число / URL и т.д.) по схеме.

### 5.4. Загрузка изображений в S3

- Несколько файлов на компонент ✅ (ссылки сохраняются в `data.images`).
- Способ загрузки: через API-роут сервера.
- Ограничения: максимальный размер на файл — 4.5 МБ (лимит тела запроса в serverless-функции Vercel), количество — до 10 шт. на один компонент.
- Превью/оптимизация: через `next/image` (ресайз и оптимизация на лету, без хранения отдельных файлов превью). Требуется настроить `images.remotePatterns` в `next.config` под домен S3.

### 5.5. Аутентификация ✅

- Регистрация: открытая.
- Вход по логину / паролю (несколько пользователей, у каждого свой каталог).
- Защита всех страниц и API (кроме страниц входа / регистрации).
