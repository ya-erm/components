# Полный бекап Components из S3 в Telegram

Автономная папка: приложение на Vercel и его зависимости менять не требуется.
Node.js **20.19+**, npm. Архивы `.tar.gz` **без шифрования**.

## Что отправляется

Команда `/backup` и ежедневный запуск присылают альбом из двух документов
с общей подписью:

- `data.tar.gz`: все текущие объекты бакета, кроме `public/images/`, включая
  `users/index.json`, каталоги, заказы, проекты и хеши паролей.
- `photos.tar.gz`: все текущие объекты `public/images/`, включая фотографии,
  которые уже не используются в карточках.

Оба архива содержат `manifest.json`: исходные ключи S3, метаданные объектов,
размеры и SHA256. Сами объекты — в `objects/00000000` и т.д., чтобы ключи S3
не могли записать файл за пределами папки при распаковке.
Отпечаток набора фотографий в манифестах связывает два архива.
Если фото не менялись, бот повторно отправляет предыдущий документ по `file_id`:
в чате по-прежнему появляется полный комплект, повторная загрузка фото в
Telegram не нужна. Из S3 пока каждый раз скачивается весь набор для проверки.

Сначала скачиваются все объекты, потом повторно проверяется список S3. Для
каждого GET передаётся `If-Match`. Если объекты менялись, создавались или
удалялись во время бекапа, запуск завершается ошибкой, архив не объявляется готовым.
Это проверка стабильности набора, а не транзакционный snapshot всего бакета.
После сжатия каждый архив распаковывается во временную папку и проверяется.
Исходный бакет при бекапе никогда не изменяется.

Копируются **текущие объекты** и их ContentType, ContentEncoding,
ContentDisposition, ContentLanguage, CacheControl, пользовательские Metadata
и WebsiteRedirectLocation. История версий, object tags, ACL, политики,
CORS, lifecycle и секреты Vercel в архив не входят. Код и конфигурация бакета
хранятся отдельно в репозитории (`infra/`). При смене адреса бакета ссылки
на картинки внутри каталогов потребуется перенести отдельно.

## Локальная подготовка

```sh
cd components-backup
npm ci --ignore-scripts
# Создаёт собственный .env из ../.env: только BOT_TOKEN и S3_* из allowlist.
# Не перезаписывает существующий файл. CHAT_ID — числовой ID личного чата.
node cli.mjs init-env CHAT_ID
node cli.mjs discover
node cli.mjs once
```

`once` только создаёт и проверяет локальные архивы. `once --send` также
отправляет их в Telegram. `bot` запускает `/backup` и расписание.
`send /path/to/components-DATE-ID` повторно проверяет и отправляет уже готовый
комплект без скачивания из S3. Перед отдельным запуском `send` остановить сервис,
чтобы не выполнять две операции одновременно, а после отправки запустить снова.
`discover` читает `/start` без подтверждения/удаления updates и не назначает
первого написавшего администратором. Для команды проверяются одновременно
личный `chat.id` и `from.id`; посторонние сообщения игнорируются.

Собственный `.env` и `data/` исключены из Git. Файлы секретов — 0600,
папка данных — 0700. Не включайте `.env` или каталог проекта в сам архив.
Для теста Telegram на Mac через существующий API сервера:

```sh
ssh -N -L 127.0.0.1:18081:127.0.0.1:8081 backup-host
# Во втором терминале, в components-backup/:
TELEGRAM_API_BASE_OVERRIDE=http://127.0.0.1:18081 node cli.mjs discover
```

По умолчанию API — `http://127.0.0.1:8081`, лимит файла 1900 МБ.
Для больших файлов нужен локальный `telegram-bot-api` с `TELEGRAM_LOCAL=1`.
Загрузка идёт потоком multipart, поэтому не требует общего Docker volume
с контейнером API и не помещает архив целиком в память.
Облачный API тоже поддерживается: `TELEGRAM_API_BASE=https://api.telegram.org`,
`TELEGRAM_MAX_FILE_MB=49`. Архив сверх лимита сохраняется на диске,
отправка завершается ошибкой. Автоматического разбиения пока нет.

## Настройки

См. `.env.example`. `BACKUP_TIME_UTC=02:00` — ежедневная проверка в 02:00 UTC;
пустое значение отключает расписание. Если бот запущен после этого времени,
он выполнит пропущенный запуск за текущий день. Время последней попытки
сохраняется в `data/bot-state.json`; ошибка не вызывает бесконечные повторы.
Повторить вручную можно через `/backup`, следующий плановый запуск — завтра.

Если список объектов бакета не изменился с последней успешной отправки,
плановая проверка ничего не отправляет и не скачивает фотографии. Сравниваются
ключи, ETag, размеры и даты изменения **всех объектов**, включая данные и фото.
Даже без изменений полный комплект отправляется после семи суток с последней
успешной отправки. Изменения вызывают отправку в ближайший ежедневный запуск.
Ручной `/backup` отправляет полный комплект всегда и тоже обновляет дату
последней успешной отправки. Состояние хранится в `data/last-success.json`
и переживает перезапуск; неудачная отправка его не обновляет.

`BACKUP_KEEP=14` хранит последние 14 **успешно отправленных комплектов** на
сервере. Неотправленные комплекты сохраняются для диагностики/повторной
отправки. Локальные тестовые `once` тоже не удаляются автоматически.
Это ограничение числа комплектов, а не дней: ручные команды тоже учитываются.
При успехе бот присылает только альбом с двумя архивами; при ошибке — уведомление.
Ежедневные отправки и сообщения об их ошибках приходят без звука
(`disable_notification=true`). Ручная команда `/backup` использует обычные уведомления.

## Перенос на сервер через rsync

Отдельная папка сервера: `/opt/components-backup`.
Следующие команды выполняются **на Mac из components-backup/**:
`backup-host` — пример SSH-алиаса; замените его на свой хост.

```sh
# Создать отдельного непривилегированного пользователя и папки:
ssh backup-host 'id components-backup >/dev/null 2>&1 || useradd --system --home-dir /opt/components-backup --shell /usr/sbin/nologin components-backup'
ssh backup-host 'install -d -m 0750 -o components-backup -g components-backup /opt/components-backup; install -d -m 0700 -o components-backup -g components-backup /opt/components-backup/data'

# Только runtime-файлы, без local data/node_modules/секретов и без --delete:
rsync -av --include='/*.mjs' --include='/package.json' --include='/package-lock.json' --include='/components-backup.service' --include='/README.md' --include='/.env.example' --exclude='*' ./ backup-host:/opt/components-backup/
# Секреты отдельно, уже с ограниченными правами:
chmod 0600 .env
rsync -av .env backup-host:/opt/components-backup/.env
ssh backup-host 'chown -R components-backup:components-backup /opt/components-backup; cd /opt/components-backup && runuser -u components-backup -- npm ci --omit=dev --ignore-scripts --no-fund'
```

Для обновления уже работающей копии сначала остановить **только**
`components-backup`, выполнить rsync/runtime install, затем снова запустить.
`data/` не синхронизируется, `.env` не перезаписывается без необходимости.

При первом переходе этого бота с облачного API на локальный нужна команда
`logOut` в облачном API. Она включена в отдельную явную команду, автоматически
при каждом старте ничего не переключается:

```sh
ssh backup-host 'cd /opt/components-backup && runuser -u components-backup -- node cli.mjs use-local-api'
ssh backup-host 'install -m 0644 /opt/components-backup/components-backup.service /etc/systemd/system/components-backup.service; systemctl daemon-reload; systemctl enable --now components-backup'
ssh backup-host 'systemctl status components-backup --no-pager; journalctl -u components-backup -n 30 --no-pager'
```

После запуска написать `/backup`, проверить **оба** документа в Telegram,
проверить совместимость архивов командой `verify` и восстановить их в отдельный тестовый бакет.
Одновременно запускать только один poller этого бота. `data/lock-pid`
показывает PID владельца блокировки. Lock обновляется каждые 10 секунд;
после SIGKILL/перезагрузки через минуту блокировка автоматически устаревает,
и systemd сможет перезапустить процесс. Обычная остановка ждёт текущую
загрузку и снимает lock сразу. Блокировку вручную удалять не требуется.

`enable --now` включает сервис в автозапуск: после перезагрузки он продолжает
работать с сохранённым расписанием и состоянием в `data/`. Docker и контейнер
локального Bot API также должны иметь автозапуск (например, `unless-stopped`).
При временной недоступности API systemd перезапустит бота.

## Проверка и восстановление

Скачать из одного комплекта оба файла (фото могут повторно использоваться
между комплектами). Проверка не требует доступа к S3 и ничего не записывает в бакет:

```sh
node cli.mjs verify /path/to/data.tar.gz /path/to/photos.tar.gz
```

Проверяется также совместимость пары по бакету и отпечатку фотографий.
Можно передать один архив для независимой проверки его файлов.

На сервере рядом с архивами также есть `summary.json` и `SHA256SUMS`:

```sh
cd data/components-DATE-ID
sha256sum -c SHA256SUMS
```

Создать отдельный **тестовый** бакет и настроить для него ключ с правом записи,
затем выполнить из components-backup/:

```sh
node cli.mjs restore /path/to/photos.tar.gz --target-bucket components-restore-test --write
node cli.mjs restore /path/to/data.tar.gz --target-bucket components-restore-test --write
```

Проверяются все файлы до первой записи. Сохраняются исходные S3-ключи и
указанные метаданные. Существующие объекты с теми же ключами перезаписываются;
лишние объекты целевого бакета не удаляются. Восстановление не транзакционно:
при сетевой ошибке может быть частичным, повторный запуск допустим.
Для исходного бакета дополнительно требуется `--allow-original`.
После восстановления сверить список, размеры и байты объектов, вернуть
политику публичного доступа **только** для `public/*` из `infra/`, затем
проверить вход, каталоги и фото в приложении.

Тесты утилиты: `npm test`. Приложение и сервер Vercel для них не запускаются.
