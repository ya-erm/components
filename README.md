# Склад компонентов

Веб-приложение для учёта электронных компонентов на складе. Mobile-first, у каждого пользователя свой каталог. Карточки в стиле маркетплейса, фото и данные в S3-совместимом хранилище.

## Стек

- **Next.js 15** (App Router), React 19, TypeScript
- **Tailwind CSS v4**
- **S3-совместимое** хранилище (AWS S3 / Yandex Cloud / MinIO) — для фото **и** пользовательских данных
- **Auth.js v5 (NextAuth)** — вход по логину/паролю (Credentials + JWT)

## Модель данных

Все данные хранятся в S3 (без базы данных):

| Ключ | Содержимое |
| --- | --- |
| `users/index.json` | `{ byLogin: {…}, byId: {…} }` — все пользователи |
| `users/{userId}/catalog.json` | каталог v2: компоненты, общие заказы и проекты |
| `public/images/{userId}/{uuid}.ext` | загруженные фото (публичный доступ) |

Набор полей компонента фиксирован в `lib/schema.ts`: `name`, `images[]`, `purchases[]`, `usages[]`, `comments[]`, `type`, `tags[]`, `note`, `url`.

В разделе «Заказы» каждая запись `purchases` содержит количество и статус: «Запланировано», «В пути», «Доставлено», «Отменено». Отменённые позиции не увеличивают остаток. Название или номер вводится один раз; трек-номер виден в одном поле без раскрытия. Ранее сохранённые несколько треков остаются в этом поле через запятую. Ссылка и комментарии доступны в раскрываемом блоке. Новый заказ создаётся непосредственно у компонента, без выбора из списка. Существующие связи между компонентами и общими заказами (`orders`) сохраняются для совместимости. Статус и количество относятся к позиции компонента, поэтому части одного заказа могут быть доставлены в разное время.

В разделе «Использование» запись `usages` содержит проект и использованное количество. Проекты (`projects`) общие для каталога; страница `/projects` показывает все компоненты, использованные в каждом проекте. Проект создаётся при добавлении использования и затем доступен у остальных компонентов.

Доступный остаток вычисляется как доставленное количество минус использованное. Запланированные заказы и заказы в пути его не увеличивают. Сохранение не допускает использование сверх известного доставленного количества. Пустое количество означает неизвестное; такие записи не превращаются в ноль. Карточки и фильтры отдельно показывают остаток, путь, планы и использование.

Старые форматы поддерживаются: складские и использованные количества становятся доставленными заказами, использование привязывается к общим проектам по названию. Треки старых посылок переносятся в заказы. Исходные `inventory`, `history`, `shipments` сохраняются как архив, без отдельных полей посылки в интерфейсе. Противоречивые старые состояния требуют уточнения. Преобразование выполняется при чтении и сохраняется при следующей записи; экспорт включает новые записи и архив, импорт проверяет связи и остаток до записи.

## Импорт из AliExpress

В каталоге есть ссылка «AliExpress», в настройках — «Импорт из AliExpress» (`/components/import/aliexpress`). Загрузите JSON экспортера версии схемы 1 (до 4 МБ), выберите заказы или отдельные товары, сопоставьте их с компонентами и проверьте изменения перед сохранением. При каждой загрузке файла все галочки сняты. Заказы отсортированы от новых к старым; доступны поиск, фильтр по дате и признаки «Новый», «Есть изменения», «Без изменений», «Нужно уточнить». Выбор не пропадает при фильтрации, счётчик включает скрытые выбранные товары.

Можно создать компонент, добавить новую покупку существующему компоненту или связать товар с покупкой, уже внесённой вручную. Для упаковок задаётся число штук: 2 упаковки по 10 дают 20 компонентов. Связи сохраняются в `purchases[].aliexpress`, данные заказа и доставки — в `orders[].aliexpress`; обычный экспорт/импорт каталога и резервные копии сохраняют их.

Повторная загрузка находит покупки по номеру заказа AliExpress, ссылке товара и варианту, независимо от порядка строк и рекламных параметров URL. Она не прибавляет количество повторно и не создаёт дубль. Неполные и повторяющиеся позиции требуют ручного сопоставления при каждой загрузке: индекс строки служит только для выбора в текущем файле, автоматическая привязка по нему не выполняется.

Автоматическое обновление сохраняет названия, заметки, теги, изображения, комментарии, проекты и ручные исправления количества/статуса. Пустые значения не стирают известные; старые выгрузки не обновляют данные автоматически. Треки объединяются, сведения из кэша только заполняют пустой список. `Completed` означает доставленную покупку, `Awaiting delivery` — покупку в пути, `Canceled` — отменённую; неизвестный статус требует уточнения. Статус покупки можно выбрать вручную в импорте. Обратный переход из доставленного или отменённого состояния автоматически не выполняется. Подробности перевозчика и последнего события видны в предпросмотре, в том числе если они расходятся со статусом заказа.

Анализ и предпросмотр ничего не записывают. Применение повторно сравнивает каталог с предпросмотром и использует условную запись S3 по ETag; конфликт возвращает 409 и требует нового предпросмотра. Все выбранные изменения проходят проверку связей и остатков до одной записи каталога. S3-хранилище должно поддерживать `If-Match` / `If-None-Match`.

`pnpm test` проверяет повторные выгрузки, варианты, упаковки, ручные правки, неполные данные и совместимость экспорта. `node tests/aliexpress-api-fixture.mjs` проверяет новый API на локальном тестовом S3 и пользователе `fixture-demo`, включая конфликт предпросмотра и условную запись. Для этих проверок используйте только тестовый dev-сервер, описанный ниже.

## Быстрый старт (локально)

Нужны Node.js 20+ и Docker.

```bash
# 1. Поднять MinIO (S3-совместимое хранилище)
docker-compose up -d

# 2. Переменные окружения
cp .env.example .env
# Заполни S3_* и AUTH_SECRET (openssl rand -base64 32)

# 3. Зависимости
pnpm install

# 4. Залить демо-данные в S3
pnpm db:seed    # пользователь demo / пароль demo12345 + 32 компонента

# 5. Запуск
pnpm dev        # http://localhost:3000
```

Демо-аккаунт: **логин `demo`, пароль `demo12345`** (или зарегистрируйте свой).
Консоль MinIO: http://localhost:9001 (`minioadmin` / `minioadmin`).

## Скрипты

| Команда | Действие |
| --- | --- |
| `pnpm dev` | дев-сервер |
| `pnpm build` | прод-сборка |
| `pnpm start` | запуск прод-сборки |
| `pnpm typecheck` | проверка типов |
| `pnpm test` | проверки миграции, остатков и перемещений |
| `pnpm db:seed` | записать демо-данные в S3 |

Для проверки без рабочего S3 есть `tests/s3-fixture.mjs`: локальное хранилище в памяти, порт 19000, пользователь `demo / demo12345`. Команда запуска dev-сервера с тестовым бакетом указана в начале файла. `node tests/api-fixture.mjs` проверяет общие заказы и проекты, остаток, фильтры, валидацию и повторный импорт. Проверка требует именно тестового пользователя и каталога; данные исчезают при остановке хранилища.

## Переменные окружения

См. `.env.example`. Ключевые:

- `AUTH_SECRET` — секрет Auth.js (`openssl rand -base64 32`).
- `S3_ENDPOINT` — пустой для AWS; для YC: `https://storage.yandexcloud.net`; для MinIO: `http://localhost:9000`.
- `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`.
- `S3_FORCE_PATH_STYLE` — `true` для MinIO/YC.
- `S3_PUBLIC_URL` — базовый URL для публичных фото (без слеша); хост добавляется в `images.remotePatterns`.

## Загрузка изображений

Файлы льются на сервер через `POST /api/upload` (по одному — лимит ~4.5 МБ serverless), сохраняются под `public/images/...` в S3. До 10 фото на компонент. Превью через `next/image`.

## S3: публичность и безопасность

Политика бакета открывает анонимное чтение **только на `public/*`** (фото). Пользовательские данные (`users/*`) приватны и читаются только с сервера по ключам SDK. Шаблон политики: `infra/yc-bucket-policy.json`. Подробнее: `infra/README.md`.

## Деплой на Vercel

1. Публичный GitHub-репозиторий (`.env` в `.gitignore`).
2. В Vercel задать переменные: `AUTH_SECRET`, `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_FORCE_PATH_STYLE`, `S3_PUBLIC_URL`.
3. Build command: `pnpm build` (без миграций — БД нет).
4. После первого деплоя запустить сид: `pnpm db:seed` локально с прод-переменными (или добавить как release command).

## Безопасность

- Пароли хешируются (bcrypt), хранятся в `users/index.json` в приватной части S3.
- Все страницы и API закрыты авторизацией (`middleware.ts`).
- Каталог компонентов скоуплен по `ownerId` — чужой каталог недоступен.
- Секреты только в `.env` / Vercel env vars.
